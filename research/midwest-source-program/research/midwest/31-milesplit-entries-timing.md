### Source

MileSplit (FloSports, Inc.) state subdomains — the same single-platform 12-host network described
in report 27; no new host, API or product was discovered in this run. Hosts exercised here:
`mi|ia|mo|ne|nd|sd|oh.milesplit.com`, all server-rendered HTML on the shared template
(`Generated by 10.1.2.x`, `data-cacheKey="{meet:<id>}:/meets/…/timing:::mo"` cache keys show the
route is server-side rendered per subpage, not a client-side shell).

Three distinct MileSplit surfaces are involved and are **not** interchangeable:

| surface | route | what it is |
|---|---|---|
| entry list | `/meets/<MeetID>/entries` | per-event entry tables (`Athlete \| Seed \| Team`) when the meet manager has published them |
| timing | `/meets/<MeetID>/timing` **and** `/<st>/timing` **and** `div.timingCompany` | the per-meet route renders the meet shell ("Meet Information" / "Meet Manager"); the state `/<st>/timing` is the timer-org directory; the attribution block links the meet to its timer |
| raw results | `/meets/<MeetID>/results` → `/results/<RSID>/raw` | fixed-width or tab-separated whole-meet results text |

### Enumeration

**Meet discovery (unchanged recipe, re-verified on 6 new states, 12/12 HTTP 200):**


### Athletic.net leverage

Unchanged in kind from report 27: **MileSplit exposes no Athletic.net hrefs, ids, or URLs** anywhere
in the 80 captures this run (0 `athletic.net` matches in any capture). Its leverage stays
tuple-shaped: `(name, school, state, grad year)` seeds a deterministic Athletic.net lookup, and the
surfaces in scope here contribute as follows.

- **Raw results are the only fully free, whole-meet result surface** in this comparison: one request
  returns every athlete/mark/place/team in the meet. Per meet that is 1 `/results` shell + 1 `/raw`
  fetch; for the 19 meets probed here that is 40 requests for 19 whole result sets (report-27's
  trade-off table still applies: no ResultID/AthleteID/TeamID/wind in the compliant view).
- **Grade-bearing?** Only sometimes, and only in the raw view (see *Result evidence*). This run
  measured **one class-of-2027-usable raw page per state for 5 of 6 states** (grade filled ≥ 93.6 %)
  and one dud (MI, 0 %).
- **Entries add no grade at all** — even the two *visible* entry lists (KS, OH) contain zero grade
  tokens. An entry row is `name + seed + team + event + division` (+ AthleteID when linked). So the
  entries surface can seed an Athletic.net lookup but can never *prove* Class of 2027; the roster
  page (report 27's `div.column-grad-year`) remains the free grade oracle.
- **Request-avoidance estimate for the whole 12-state network:** the entries surface is worth
  probing only where the nav bit is set. On this sample (2/22 visible) that is not a discovery
  surface to budget for; on the two meets where it fired (KS state, OH indoor state) it delivered
  ~378–2,599 `(athlete, team, seed, event)` tuples in **one** request each, i.e. a whole-meet
  participant list at pre-meet time. Treat it as opportunistic upside, not a planned lane.

Consequences for the pipeline:

- **Grade is a per-meet property, not a platform property.** The MI page (`779299`) renders the
  `Yr` column header but leaves it blank on **all 971 rows** — that meet's timing data simply has no
  grade. A collector must therefore measure grade fill per raw page and fall back to the roster/profil
  join where it is 0.
- **Two grade notations** must be normalised: numeric (`6`–`12`; in a May 2026 meet `11` = Class of
  2027, in a September 2026 meet `11` = Class of 2028 — the calendar trap report 27 flagged) and
  class labels (`FR/SO/JR/SR`). The labels are ambiguous across levels: the MO raw page mixes college
  and high-school rows and both use `JR`. Class-label rows therefore need discipline/name context
  before they mean a graduating cohort.
- **Relay membership is layout-dependent** — report 27's "relay legs are `1) A` with empty names"
  holds for the fixed-width layout, but the tab-plain layout prints **all four leg names** in the
  `Name` cell (SD outdoor state meet: 798 leg rows, e.g. `Autumn Aukes, Emory Lems, Sydney Schaap,
  Arianna Farris`). Where the SD-style layout is served, relay identity is free; where the
  fixed-width layout is served it is not.
- Everything else measured by report 27 holds: no ResultID, no EventID, no AthleteID, round in the
  event title (`… Class A - Prelims (Class A) (Prelims)`), heat only where the layout has an H#/HEAT
  column, wind only where the layout has a WIND column, no implement/hurdle specification.

### Incremental use

- **New meets:** unchanged results-browser recipe; diff `data-meet-id` sets. 12 listings × 50 rows
  were all live on 2026-09-20 and all carried a results link, so this axis finds meets *after*
  results exist.
- **Entries (opportunistic):** for each meet already fetched in the results sweep, read the nav.
  If an `Entries` item is present, fetch `/entries` once and cache
  `(MeetID → {n_events, n_pairs, snapshot_hash})`. Absent item → skip, and re-check at most once per
  meet per day (the switch is manager-controlled and could flip). Cost bound: 0 extra requests for
  the ~91 % of meets where it is hidden.

### Recommendation

**RESULT-SOURCE for raw results; DISCOVERY-ONLY (opportunistic) for entries; the `/timing` route is
an attribution/directory surface, not a data lane.** The three parts of C4 resolve as follows.

1. **Is MileSplit entries a viable grade-bearing discovery surface? No — and it is *not*
   grade-bearing anywhere.** Across 22 meet observations (this run + report 27's captures) the
   visibility rate is 2/22; hidden pages contain zero data and an explicit "hidden by the meet
   manager" string; visible pages contain `name + seed + team + event + division` (+ AthleteID when
   linked) and **no grade column at all**. It is worth wiring only as an opportunistic pre-meet
   participant list behind the nav-item gate, at ~0 marginal cost.
2. **Is MileSplit `/timing` viable?** The state directory is a clean enumerator — 88 timer orgs in
   the six states this agent probed (MO 39, MI 28, IA 10, SD 6, NE 4, ND 1), plus 107 in OH and 79 in

   `[INFERENCE]` from the shared id space plus that cross-host link; not contradicted by anything
   measured. It is a second meet-discovery axis, not an athlete/grade source. The per-meet

   shell (15 × "Meet Information", 3 × "Meet Manager" for the three MileSplit-Manager state meets),

3. **Is the raw result page viable?** Yes, with the grade caveat: whole-meet marks, names, teams,
